## Owner and administrators

At the user's explicit direction, existing account **configured-owner (UID 4)** was activated
and bootstrapped as the **single application owner**, retaining its existing real
email. No email was guessed or hardcoded in application/setup code. Local Mailpit
sign-in was tested for this account; real mailbox delivery/ownership was not tested.
Drupal's **admin (UID 1)** remains the emergency superuser, not a second application
owner. Its placeholder email is unchanged.

Roles are created only when absent, with an exact permission check on rerun;
existing roles are never overwritten:

- `lit_application_owner`: review, synchronize, publish, settings, reconciliation,
  and manage authorized administrators.
- `lit_contribution_administrator`: review private submissions and approve/reject
  with reasons. No publishing, settings, synchronization, user/role management.
- Visitors and ordinary authenticated accounts: public map only.

Restricted routes and services check ownership for privileged operations, in
addition to Drupal permissions. Owner identity is a server-side UID; public
parameters cannot assign roles/ownership. The owner interface uses Drupal forms,
CSRF protection, user entities and role/access APIs. It records actor UID, target
UID, action and UTC time. Existing legacy reviewer accounts are shown so the owner
can deactivate them without rewriting their old roles; use Add administrator for
an explicit passwordless authorization. The old QA reviewer role was preserved.

Entity hooks prevent blocking/deleting the sole owner, removing its owner role,
assigning ownership to another account, or deleting the assigned owner role.
Deactivation revokes Drupal sessions and all outstanding application sign-in links.
Role/email/password changes also invalidate outstanding links/sessions.

## Passwordless sign-in

No contributed dependency or Composer change was added. This uses Drupal core
accounts, permissions, Form API, flood service, mail API and
[`user_login_finalize()`](https://api.drupal.org/api/drupal/core%21modules%21user%21user.module/function/user_login_finalize/10)
for normal session regeneration/login hooks. Core's session-manager API revokes
sessions. Drupal 11 compatibility of this custom login wrapper is not claimed;
verify its newer login-finalizer service separately during migration.

The custom credential is a cryptographically random 256-bit one-time secret;
only its SHA-256 hash, UID, account-state fingerprint and expiry are stored.
It expires after **15 minutes**. Atomic deletion permits only one successful
redemption. Current active/authorized status is checked again before redemption.
The link's secret is in a URL fragment, never a GET path/query/referrer. A small
Drupal behavior moves it into a hidden POST field and removes the fragment from
browser history. A deliberate Confirm sign-in action consumes it. Application
logs contain no token. No token is returned by the public email-entry response.
POST-body logging/APM must remain disabled or redact this field in production.

Email entry alone never authenticates. Responses are generic for unknown,
inactive, unauthorized and throttled addresses. Limits: **5 requests/address per
15 minutes**, **20 requests/IP per hour**, and **30 redemption attempts/IP per
15 minutes**, using Drupal flood storage. Email flood keys are hashes. A fixed
local review route is the post-login target; visitor `destination` is discarded.
Links are proof of access to the development mail catcher here, not evidence of
real delivery. Authentication requires JavaScript for safe fragment handling.

This milestone's sender is intentionally local-only: DDEV, core `php_mail`, and
Mailpit's localhost sendmail transport must all match, otherwise no link is sent.
DDEV's [Mailpit capture](https://docs.ddev.com/en/stable/users/usage/developer-tools/)
was verified as `/usr/local/bin/mailpit sendmail -t --smtp-addr 127.0.0.1:1025`.
No real email integration or live Qualtrics API is configured. The survey invitation
remains **OFF**, URL **blank**. Disabling it does not close a Qualtrics survey.

## Install/update locally

Already-installed site (additive schema update; never reinstall its database):

```sh
ddev start
ddev drush updatedb -y
ddev drush cr
# Choose an existing account explicitly; 4 is the user-authorized local configured-owner account.
ddev exec env LIT_OWNER_UID=4 vendor/bin/drush php:script scripts/setup-contribution-owner.php
python3 tools/contribution/generate-mock.py --large
ddev drush php:script scripts/setup-contribution-large-demo.php
```

The generator retains its original manifest anchor and refuses differing existing
output. `--large --check` checks reproducibility without writing. To create a new
vintage later, add a distinctly versioned dataset/allowlisted path; never overwrite
reviewed source files. The runtime adapter accepts no visitor-supplied path or URL.

Fresh installation in a **new empty DDEV project/database**: follow root README
for Composer/core installation; then `ddev drush en lit_contribution -y`. Fresh
`hook_schema` creates the same tables; install configuration keeps invitation off.
Create/select the intended owner through local Drupal/Drush, then run the explicit
owner and large-demo steps above. No full-site configuration import is needed.
The current default datasets use only the local mock adapter. Private exports and
publications must be generated locally; they are not cloned from Git.

If an intended owner's email is blank/placeholder, supply the confirmed address
explicitly (replace the values; do not copy a fictional address):

```sh
ddev exec env LIT_OWNER_UID=YOUR_UID LIT_OWNER_EMAIL='YOUR_CONFIRMED_EMAIL' vendor/bin/drush php:script scripts/setup-contribution-owner.php
```

Normal local recovery without changing owner:
`ddev drush user:login --name=configured-owner --no-browser`.
Emergency Drupal administration: `ddev drush user:login --uid=1 --no-browser`.
Never share or commit the printed one-time URL.

Server-side repair/transfer if the owner account becomes unusable: select a
confirmed existing UID, then run the following explicit recovery action. It
removes the old application-owner role, activates/assigns the new owner, revokes
sessions/tokens, and writes an audit event. UID 1 is retained. This is never called
by a public page and was **not executed against this site's owner** during QA.

```sh
ddev exec env LIT_CONFIRM_OWNER_RECOVERY=yes LIT_OWNER_UID=CONFIRMED_UID vendor/bin/drush php:script scripts/recover-contribution-owner.php
ddev drush cr
```

1. Owner enters its existing email on Sign-in. Open the captured message in Mailpit,
   follow its link, and confirm. This establishes a Drupal session.
2. Owner opens management, enters an administrator email and chooses Add administrator.
3. Administrator requests its own sign-in link, reads the local captured message,
   follows the link and confirms. Entering the email alone grants no access.
4. Administrator opens the pending review queue, selects a permitted/nonduplicate
   record, records an internal reason and approves/rejects. Approval alone does not
   update the map. The queue is paged, pending-first; raw source is private.
5. Owner inspects reconciliation and confirms Publish approved aggregates. Only
   eligible active-dataset responses contribute; map refresh reads the new JSON.
6. Owner can deactivate/reactivate administrators. Deactivation ends existing
   administrative sessions and invalidates old sign-in links; reactivation requires
   a fresh link.

QA left its newly created reserved-domain administrator **inactive**. It did not
change any actual pending review decisions. The demonstration remains 10,000/100.
